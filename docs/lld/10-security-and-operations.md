# LLD-10 — Security and operations

Target: one DevOps engineer at 0.25–0.5 of full time can run the platform. To make that possible, our admin side is never public and routine work is automated.

## 1. Host hardening (Ansible role `infra/ansible/roles/base`)

- Ubuntu 24.04 LTS minimal, with automatic security updates (`unattended-upgrades`) and reboot windows Sunday 04:00 TRT.
- **SSH:**
  - key-only, no root, no passwords;
  - listens **only on the Tailscale interface**;
  - fail2ban for safety.
- **Firewall:**
  - Hetzner Cloud Firewall: allow 443 from Cloudflare IP ranges only, plus Tailscale UDP;
  - host `nftables`: same rules, default deny.
- Docker:
  - rootless where possible;
  - `userns-remap`, `no-new-privileges`;
  - read-only root filesystems for our images;
  - drop all capabilities except those needed;
  - non-root users in images.
- Time sync (chrony), and `auditd` for privileged commands.

## 2. Edge

- **Cloudflare (Pro):**
  - proxied DNS;
  - WAF managed rules;
  - DDoS protection;
  - Bot Fight mode;
  - per-tenant country rule (LLD-02);
  - rate limiting on `/oauth/*`, `/api/auth/*`, `/hooks/*`.
- **Traefik:**
  - HSTS, security headers middleware (CSP for console);
  - `ipAllowList` per tenant;
  - `rateLimit` per IP for login routes.
- **TLS:** Cloudflare Full (strict) using origin certificates.

## 3. Secrets

- SOPS + age encrypted env files in git. Age keys:
  - one per engineer;
  - one per host, stored root-only.
- **Rotation runbook (90 days):**
  - LiteLLM master key;
  - provider API keys;
  - Keycloak admin;
  - database passwords;
  - Cloudflare API token.
- Tenant secrets (OIDC client secret, gateway key, CREDS_KEY/IV, JWT) are generated by the provisioner, never shown again, and rotatable with `tenant:rotate-secrets`.
- Phase 2: OpenBao for per-tenant encryption keys (Studio tool credentials, connector tokens).

## 4. Backups and restore

| Data | Method | Frequency | Retention |
| --- | --- | --- | --- |
| Postgres (all DBs) | `pg_dump` per database + WAL archiving (pgBackRest or wal-g) | nightly + continuous WAL | 30 daily, 12 monthly |
| MongoDB | `mongodump --db lc_<slug>` per tenant | nightly | 30 daily |
| SeaweedFS / uploads | restic | nightly | 30 daily |
| Configs (rendered, encrypted) | git + restic | on change | – |

- **Target:** Hetzner Storage Box (EU) / Turkish storage for the TR region, encrypted by restic.
- **Monthly automatic restore test:** restore to a scratch compose project and run a smoke test. An alert fires if the test fails or is missing.
- **Objectives:** RPO 24 h (Mongo) / 15 min (Postgres with WAL); RTO 4 h for a full host loss.

## 5. Monitoring and alerting

- Prometheus + node-exporter + cAdvisor + Postgres/Mongo/Valkey exporters; Loki + Promtail for logs (JSON, no PII); Grafana dashboards per service and a per-tenant overview.
- **Alerts** go to Telegram/phone and email:
  - host down;
  - disk over 80%;
  - certificate expiry within 14 days;
  - gateway 5xx over 2% for 5 min;
  - upstream provider error rate;
  - p95 latency;
  - Valkey memory;
  - backup missing;
  - restore test failed;
  - failed-login spike (Keycloak events);
  - budget anomaly (tenant spend over 3× its 7-day average);
  - provisioner job failed.
- **External uptime check** of `status.<domain>` and 2 tenants (Better Stack free tier or Uptime Kuma on a separate small VM).

## 6. Vulnerability management

- **CI:** Trivy image scan, `pnpm audit`, a licence check and gitleaks (secret scan).
- **Weekly:** Renovate PRs; a Nuclei / OWASP ZAP baseline scan against `test`.
- **Yearly:** external pentest (budget about $5,000). Fix high findings within 14 days, critical within 72 h.
- **Supply chain:**
  - LiteLLM built from a pinned source tag;
  - checksum verified;
  - upgrade only after reading release notes and security advisories.

## 7. Incident response (short runbook)

1. Detect (alert or report), then open an incident note in the `incidents/` repo folder (template).
2. **Contain:**
   - revoke keys (provider, gateway, tenant);
   - block IPs at Cloudflare;
   - suspend the tenant if needed.
3. **Assess personal-data impact.** If personal data is affected, notify the KVKK Board within 72 hours (verify the current rule with counsel) and notify affected tenants.
4. Recover from backups if needed, then write a post-mortem within 5 days.

## 8. KVKK operational controls

- VERBIS registration and a data inventory (processing activities: chat content, usage logs, identity).
- A data processing agreement (DPA) template for customers, plus a sub-processor list (each LLM provider, Hetzner, Cloudflare, Lago host, e-Fatura provider).
- Cross-border transfer: EU-region tenants get a disclosure plus the appropriate KVKK transfer mechanism (counsel to confirm). The TR region keeps all data and models in Turkey.
- Retention defaults:
  - chats: tenant-defined (default 12 months);
  - usage events: 24 months;
  - audit log: 5 years;
  - backups: 30 days.

## 9. Acceptance criteria

- An external port scan of each host shows only 443 (through Cloudflare); SSH is not reachable from the internet.
- A restore test succeeds on schedule, and the alert fires when it is disabled.
- Gitleaks and Trivy block a PR that adds a test secret or a known-critical CVE image.
- The incident runbook has been rehearsed once (tabletop) before the pilot.
